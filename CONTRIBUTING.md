# Contributing to `prv`

Thank you for your interest in contributing to `prv`! We welcome contributions from the community.

Please take a moment to review this document to understand our development workflow, coding standards, and contribution guidelines.

---

## 📜 Code of Conduct

All contributors and participants are expected to adhere to our [Code of Conduct](CODE_OF_CONDUCT.md). Please read it to understand our community standards.

---

## 🛠️ Development Setup

### 1. Prerequisites
- **Go**: Version 1.26+ (or 1.27) installed on your system.
- **Git**: Version 2.30+.
- **GitHub CLI (`gh`)**: (Optional, but recommended for PR integration and reviews).

### 2. Clone the Repository
```bash
git clone https://github.com/vubon/prv.git
cd prv
```

### 3. Build & Install Locally
```bash
# Verify formatting, lint, and run tests
make check

# Build binary into ./bin/prv
make build

# Install into your $GOPATH/bin
make install

# Smoke test
./bin/prv --version
./bin/prv --help
```

## 🧪 Testing & Code Quality

Before submitting a Pull Request, verify that all pre-commit quality gates pass with zero errors:

### 1. Run Complete Check Suite (Format, Lint & Tests)
```bash
make check
```
`make check` executes:
1. `fmt-check`: Verifies `gofmt -l .` reports zero unformatted files.
2. `lint`: Runs `go vet ./...` (and `golangci-lint` if installed).
3. `test`: Runs table-driven unit tests across all packages.

### 2. Code Coverage
```bash
# Run tests with coverage profile
make test-coverage

# Generate and view HTML coverage report
make coverage-html
```

### 3. Auto-Format Code
```bash
make fmt
```

## 🔄 Development Workflow

### 1. Branch Naming
Create a feature branch from `main`:
```bash
git checkout -b <type>/<short-description>
```
Follow standard prefixes:
- `feat/` — New feature or major enhancement (e.g. `feat/gitlab-api-support`)
- `fix/` — Bug fix or correction (e.g. `fix/diff-line-offset`)
- `docs/` — Documentation updates (e.g. `docs/cli-examples`)
- `test/` — Adding or refactoring unit tests (e.g. `test/github-api-mock`)
- `chore/` — Tooling, CI, dependencies, or maintenance (e.g. `chore/ci-runner-update`)

### 2. Self-Review with `prv` Before Committing
`prv` includes its own pre-commit review command! Use it to inspect your uncommitted changes before pushing:
```bash
# Stage your changes
git add internal/ pkg/

# Generate pre-commit review bundle against repo rules and sensitive files
./bin/prv bundle --staged

# Generate architecture diagram for your changes
./bin/prv diagram --staged
```

### 3. Commit Messages (Conventional Commits)
Write concise commit messages following the [Conventional Commits](https://www.conventionalcommits.org/) format:
```
<type>(<scope>): <description>

[optional body]

[optional footer]
```
**Examples:**
- `feat(review): implement line-level inline diff comments`
- `fix(git): resolve path quoting in unified diff parser`
- `docs(readme): add interactive Mermaid architecture diagram`

## 💬 Conventional Comments Standard

All review feedback generated by or submitted to `prv` adheres strictly to the [Conventional Comments](https://conventionalcomments.org) specification:
```
<label> [decorations] (<subject>): <title>

[discussion / explanation]

```suggestion
[exact drop-in replacement code]
```
```

Labels include `🚨 blocking`, `⚠️ issue`, `🔒 security`, `⚡ performance`, `💡 suggestion`, `🔍 nit`, `❓ question`, and `👏 praise`.

## 📦 Pull Request Checklist

Before opening your Pull Request, verify:
- [ ] Branch is rebased onto the latest `main`.
- [ ] `make check` passes with 0 errors and 100% tests passing.
- [ ] Unit tests are added or updated in `*_test.go` covering new logic and edge cases.
- [ ] Documentation (`README.md`, `docs/`) is updated if CLI flags or behaviors changed.
- [ ] `CHANGELOG.md` has an entry under `[Unreleased]` describing the change.
