# Cursor IDE Setup Guide

This guide explains how to configure **Cursor IDE** (and Cursor Composer / Agent) to use `prv` for Pull Request and branch reviews.

---

## 1. Modern Cursor Rules (`.cursor/rules/prv-review.mdc`)

Cursor supports directory-level MDC rules in `.cursor/rules/`. Create `.cursor/rules/prv-review.mdc` in your repository:

```markdown
---
description: PR and code review workflow using prv context engine
globs: *
alwaysApply: false
---

# Code & PR Review Rules (prv)

When asked to review a branch, PR, or diff:

1. **Generate Context Bundle:**
   Run the terminal command:
   - For current branch against custom base: `prv bundle --base <base_branch>` (e.g., `staging`, `dev`)
   - For uncommitted staged changes: `prv bundle --staged`
   - For local branches against custom base: `prv bundle --branch <branch_name> --base <base_branch>`
   - For local branches against default base: `prv bundle --branch <branch_name>`
   - For remote GitHub PRs: `prv bundle --pr <number_or_url>`
   
   If a custom `.prv.yaml` configuration is used:
   `prv bundle --config .prv.yaml`

2. **Respect Repository Standards:**
   - Adhere strictly to any custom team rules listed under `## 📋 Team Engineering Standards & Custom Rules (.prv.yaml)`.
   - Pay extra attention to any files marked `🚨 [SENSITIVE]` or listed under `> [!CAUTION] Security Sensitive Paths Touched`.

3. **Evaluate against the 11 Pillars:**
   - Intent & Spec Alignment
   - Logic & Bug Detection (nil checks, unhandled errors, concurrency races)
   - Security & Data Safety (OWASP, injection, leaks)
   - Performance & Scalability (N+1 queries, unclosed bodies)
   - Testing & Verification
   - Clean Code & Style
   - Architecture & System Coupling
   - Observability & Operability
   - Blast Radius & Failure Modes
   - Data Contract & Migration Safety (schema migrations, breaking serialization)
   - Environment & Configuration Hygiene (environment variables, config fallbacks)

4. **Deliverable Requirements:**
   Every review MUST include:
   - **🎯 Weakest Link in the Change:** Where and how this code will break under stress.
   - **⚖️ Architectural Trade-offs:** Compromises made in this design.
   - **🗺️ Architecture & Component Impact Diagram:** Mermaid graph generated via `prv diagram --markdown` or bundle context.

5. **Comment Format:**
   Use the Conventional Comments format:
   `🚨 blocking`, `⚠️ issue`, `🔒 security`, `⚡ performance`, `💡 suggestion`, `🔍 nit`
   with exact file and line references (`path/file.go#L42`) and copy-ready GitHub suggestion blocks (` ```suggestion `).

6. **Publishing Safeguard (Human-in-the-Loop):**
   Always present the review findings to the user first. Do NOT run `prv report --post` or `gh pr comment` until the user explicitly asks to post the comment.
```

---

## 2. Legacy Cursor Rules (`.cursorrules`)

If your team uses the root `.cursorrules` file, append the following block to your `.cursorrules`:

```markdown
# prv Review Engine
When asked to review code, PRs, or branches:
1. Run `prv bundle --staged` (for staged pre-commit diffs), `prv bundle --branch <branch>`, or `prv bundle --pr <url>` via terminal.
2. Read the filtered diffs, team rules, and 11-dimension checklist generated by prv.
3. Identify the "🎯 Weakest Link", "⚖️ Architectural Trade-offs", and include a Mermaid architecture diagram (`prv diagram --markdown`).
4. Output findings using Conventional Comments with line numbers and ```suggestion blocks.
```

---

## 3. Usage in Cursor Composer / Chat

In Cursor (Cmd+K, Cmd+I, or Composer Agent):

```
"Review my staged changes with prv before I commit"
"Run a pre-commit review on staged files"
"Review my current branch feat/auth-tokens with prv"
"Review GitHub PR #14 using prv bundle"
"Check this diff for security risks and identify the weakest link"
```
Cursor's Agent will execute `prv bundle`, ingest the structured output, and provide a staff-engineer level review report.
